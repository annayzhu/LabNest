## 2. PIP-12-01：先明确“实际要移哪一份液体”

### 2.1 核心规则

移液下限针对**一次实际加入、转移或分装的体积**。下列量不应直接当成单次移液：

- 预混组分在单反应中的理论当量；
- 一批液体的库存需求或汇总量，除非确实是配制该批次时的加入步骤；
- 目标总体积、定容刻度、转移后的剩余体积；
- 以克、毫克等表示的称量质量；
- 没有被用户采用的替代方案，或被实际舍入方案取代的旧操作。

示例：每反应酶当量0.1 μL，100个反应共同预混，实际向预混管加入酶10 μL。移液检查对象为10 μL；反应组成表仍可展示0.1 μL，但必须标为“每反应当量”，不能写成“逐管加酶0.1 μL”。

“实际步骤”表示计划中的执行粒度，不声称用户已完成移液，也不意味着已经做了移液器步进舍入。不要继续用单一 `basis: theoretical/actual` 同时表达这两种不同含义。

### 2.2 数据契约

优先扩展现有 `LiquidOperation` 与规划层，不要求复制一套引擎。字段名称可适配当前类型，以下语义必须具备：

| 字段语义 | 要求 |
| --- | --- |
| 稳定操作 ID | 唯一到计划、组、样本、组分及动作；不因中英文或显示单位切换改变 |
| 动作 | 加入、转移、分装；定容单独表达，不伪造为固定加液量 |
| 来源与去向 | 能区分母液→预混管、预混管→反应孔、模板→单独反应孔 |
| 组分／样本／组 | 使用结构化标识；显示名称只用于界面 |
| 一次操作体积 | 有限非负数＋可转换的体积单位；内部复用规范单位体系 |
| 重复次数 | 若压缩表达重复动作，应为非负整数；只检查每次量，不能用次数乘积代替 |
| 数值性质 | 未舍入计划量或已采用的舍入量；与是否为执行步骤分开 |
| 关联 | 可追溯到输入行、结果行及所采用的计划版本 |

要求：

1. 从规划结果／类型化组分数据生成操作，不通过 `labelZh`、中文“是”、`perReactionUl` 字段名后缀猜测是否预混。
2. 可采用每工具适配器，但必须有集中覆盖清单。新增有液体操作的工具而缺少适配时，开发测试必须失败。
3. 未支持的液体任务不能以空数组冒充“全部移液检查通过”；状态明确为“未完成移液检查”。纯换算工具可明确为“不适用”。
4. 中英文名称、单位格式、表格排序和图标套件只改变展示，不改变操作语义。
5. 优先让规划层同时提供显示表与操作数据，避免界面、导出、警告各自重新计算数量。
6. 大批次允许“每次2 μL，重复100次”的压缩表示；不同模板或样本不可因同名而合并成一个实际混液步骤。

### 2.3 计算状态与设备检查状态

- 输入矛盾、体积为负、非有限数、单位不兼容：阻止输出为有效配方，清除旧有效结果。
- 公式成立，但某个实际操作低于用户设置下限：保留数学结果，显著提示“存在低于所设移液下限的步骤”；允许带警告复制／记录，不能呈现无条件绿色“可直接执行”。
- 未设置下限：显示“未设置移液下限”，不猜测1 μL是所有设备默认下限。
- 所有操作不低于下限：最多称“通过所设移液下限检查”。本轮不推断设备上限、精度或试剂适用性。

## 3. PIP-12-02：百分浓度配液

### 3.1 必修复现例

输入：`type = v/v`，百分浓度0.1%，最终体积100 μL，移液下限1 μL。

计算：液体溶质体积 = 100 × 0.1 / 100 = **0.1 μL**。

预期：

- 有“取液体溶质0.1 μL”的操作及对应低于下限警告；
- 操作说明为“取液体溶质0.1 μL，再定容至100 μL”；
- 不将100 μL的目标刻度作为一次移液；
- **默认不把99.9 μL当成精确溶剂加入量。** 未明确体积可加和假设时，混合体积不能直接等同于体积相加；
- 如果工具已有明确选择的体积可加和近似模式，可输出估算溶剂量，但页面、复制与记录需保留该假设。

这里的液体溶质按该模式直接定义。若输入的是某浓度母液，应进入稀释模式，不能不经声明将母液当作纯溶质。

### 3.2 各模式区分

| 模式 | 处理 |
| --- | --- |
| v/v | 检查已知液体溶质取用量；定容不是精确溶剂移液量 |
| w/v | 显示称量质量及定容步骤；不把质量换算为移液体积 |
| w/w | 显示各组分质量；缺少密度不猜体积 |
| 0% | 无非零溶质加入步骤；不因0触发低量警告 |
| 100% v/v | 溶剂为0；如需量取已知溶质体积则正常检查，不能生成负量 |

若用户明确提供密度且现有功能支持质量与体积转换，按显式转换结果处理，不为完成本修复新增无来源密度表。

## 4. PIP-12-03：Master Mix

### 4.1 标准验收输入 A

100个实际反应，每反应总体积20 μL，余量0%，移液下限1 μL。

| 组分 | 每反应体积 | 是否预混 |
| --- | ---: | --- |
| 2×反应液 | 10 μL | 是 |
| 酶 | 0.1 μL | 是 |
| 水 | 7.9 μL | 是 |
| 模板 | 2 μL | 否 |

必须产生的计划：

1. 向预混管加入反应液1000 μL、酶10 μL、水790 μL，总预混体积1800 μL。
2. 向每个反应孔分装预混液18 μL，共100次。
3. 向各自反应孔加入对应模板2 μL，共100次；模板保持独立。
4. **不得针对酶的0.1 μL单反应当量报警。** 这个例题没有低于1 μL的实际计划操作。

大体积超过某支移液器上限的分次操作不在本例下限验证范围内；没有上限输入就不要擅自拆分或声称设备适配已全部通过。

### 4.2 标准验收输入 B：余量10%

沿用 A，预混准备量为110个反应当量：反应液1100 μL、酶11 μL、水869 μL，总量1980 μL。

实际仍是100个反应，每孔18 μL，实际使用1800 μL，预混余量180 μL。每孔模板仍为2 μL，不把样本数变成110，也不把独立模板用量静默乘1.1。

如用户显式另设独立样本预留量，显示“备液需求”，仍按每次实际加入量判断下限；与预混余量分开计算。

### 4.3 必须区分的步骤

| 组分／动作 | 下限检查依据 |
| --- | --- |
| 参与预混的组分 | 向该组预混管加入的批量体积 |
| 独立加样组分 | 每孔／每反应实际加入量 |
| 预混液分装 | 每孔分装的预混液量 |
| 自动补水 | 按其真实所在阶段检查：进入预混管则按批量，单孔补水则按单孔 |
| 多个反应组 | 分别配制、分别判断；不得以跨组总和掩盖某组低量 |
| 分组分装 | 每个组都必须有自己的预混分装操作；不能依赖仅单组路径存在的全局 `dispenseUl` |
| 无预混组分 | 不生成空的预混分装操作；独立加样操作仍完整 |
| 0体积组分 | 可在配方中保留“无需加入”，不产生低量警告 |

“独立模板总量足够”不能消除某次0.1 μL加样低于1 μL的问题。同一名称、不同样本ID的模板，不得混为一管。

### 4.4 物料与体积检查

每组单反应：预混分装量＋独立组分加入量 = 单反应总体积。

每组预混：批量组分之和 = 预混准备量；准备量 − 实际反应数×每反应分装量 = 余量，且不得为负。

采用适合规范单位的浮点容差；测试可使用 `max(1e-9 μL, |预期量|×1e-9)`，显示舍入不能用来计算物料平衡。余量只应用一次。

| 离心、Tm、纯单位换算、拟合分析 | 无配液操作时标记不适用 | 不因出现体积单位就推断为移液任务 |

上表用于指导检查，不宣称未列出的路径已经有缺陷。不得凭“函数未抛错”认定覆盖完成。

### 5.2 阈值、单位与舍入

- 仅 `0 < 一次操作量 < 下限` 触发低量警告；等于下限不触发。
- 下限必须正且有限；空值表示未设置。负量、NaN、Infinity应报输入／计算错误。
- 0.0001 mL、0.1 μL、100 nL必须得到相同判断；使用未显示舍入的规范值比较。
- 重复计算或切换语言／单位，不叠加重复警告。去重按操作身份，而非仅按文案。
- 若用户采用步进舍入方案，检查所采用方案的实际量；理论方案保留比较信息，但不混成当前执行步骤重复报警。
- 仅作提示的中间液方案不自动替代原方案。若支持采用，重新计算全部步骤、浓度及体积平衡；没有足够信息时只给调整方向，不猜试剂稳定性或溶剂。
- 小量被步进舍入为0，不得把原配方视为可执行；浓度偏差和补液修正必须明确。

## 6. OUT-12-01：结果和警告只有一个来源

页面、复制、CSV／已有其他导出、历史快照与“记入实验”共同使用同一结果及操作数据，不在格式化函数里独立重算。

必须保存或携带：工具及方法版本、输入及单位、结果、操作、所设移液下限、警告、定容／体积近似假设，以及采用舍入方案时的数值性质与偏差。只更新相关方法／操作模型版本，保留旧快照兼容。

- CSV可以扩展操作列，或按现有导出约定包含独立警告记录；必须自描述，不能把警告插入数值格损坏表格。
- 复制步骤保留具体组／样本／组分、操作体积、下限及警告；不能只剩笼统“请小心操作”。
- 历史没有操作字段时仍可读取，注明旧快照未记录这些信息；不自动用新算法覆盖旧结果。
- 用户明确“重新计算”才创建新的结果关联；旧快照不变。
- Appearance 切换不产生新计算历史、不修改数值、不触发实验重复同步。
- 无效输入时不得复制上一轮有效配方；合法但含低量警告的结果允许完整复制和保存，不因导出而丢警告。

## 17. 用户追加：移动端 Experiment Run 完整步骤与辅助工具

本节与v1.2正文同属必做范围。追加依据为用户本次反馈；编写时仅静态读取了历史提交的相关代码，不把它表述为最新远端版本的实测结论。

### 17.1 现状线索与目标

历史提交中，`ProtocolRunProgressForm.tsx` 的 `RunStep` 仅接收文字 `description`，手机当前步骤通过段落展示；`protocol-document.ts` 的步骤投影遍历标题、文字、富文本和清单，未在该循环中纳入表格块。`StepCalculator.tsx` 默认工具为 `dilution`，手机跳转 `/tools/calculator/${tool}`。这些是执行时需要重新核对的定位线索。

**用户需要在执行当前步骤时直接看到完整操作内容，包括配液表、材料表、注释及其前后说明；点击“计算器”先选工具，无需先退出稀释页面。**

### 17.2 RUN-12-01：完整保留步骤内容

#### A. 显示要求

1. 当前选中步骤的全部操作内容默认展开显示，不只显示标题、摘要或纯文字。允许正常纵向滚动；“完整”不要求把全部内容挤进一屏，也不要求把全部实验步骤同时展开。
2. 按源Protocol中的顺序保留段落、已有格式、列表、表格、图片／图注、提示块及链接等当前文档模型支持的节点。配液和材料表必须仍为表格，保留表头、所有行列、单位、单元格换行及已有合并关系；不得转成缺失对应关系的文字串或截图。
3. 步骤内嵌的材料／配液信息就地显示；来源于该步骤明确关联的材料块也应可见并说明关联。全局材料目录不能无差别复制到每个步骤。
4. 只读展示复用现有文档渲染能力，保持实验执行操作与编辑Protocol分开。若当前渲染器只接受完整文档，可抽取共享块渲染能力，不复制另一套不完整的富文本解析器。
5. 图片保持比例，允许查看原尺寸；附件按原有节点语义保留名称和访问入口。资源加载失败应显示明确占位／重试路径，不能无提示消失。
6. 不以固定高度、行数截断、`overflow:hidden` 或“只显示前N行”隐藏操作正文。当前步骤的关键表格不能默认折叠后要求再去打开Protocol才能看见。
7. 表格视口适配：可容纳的表格正常铺开；宽表在自身容器内横向滚动，单元格文字合理换行，保留可读字号。明确提示“左右滑动查看完整表格”；左右所有列都能触达，整页不因宽表横向溢出。
8. 不把表格强制转成丢失二维关系的卡片；可提供额外全屏查看，但步骤内必须已有完整数据的表格视图，不能仅保留“查看表格”链接。
9. 执行页仍保留既有逐项完成确认、偏差记录和证据关联。不能为展示一个完整文本块而合并原有可独立勾选的子步骤。

#### B. 修复数据链路，而不只改变样式

逐段检查：Protocol编辑／导入 → 文档保存 → 执行步骤投影 → 实验创建时的Protocol版本／快照 → Run API或服务端数据 → 客户端渲染 → 离线恢复。

- 优先复用已有结构化文档和不可变快照。步骤通过稳定块ID／步骤ID绑定其正文范围，不能依靠标题字符串匹配（同名步骤可能出现在不同组）。
- 没有现成绑定时，建立明确、可测试的映射规则：通常步骤标题后至下一同级步骤标题前的块归属该步骤；嵌套清单、子标题和独立确认项按现有语义处理，不能把材料行识别成额外步骤。
- 标题前的公共准备内容或无法明确归属的块，放在对应组内明确的“共同准备／补充内容”区域，保持可见；不能静默丢弃或任意塞到最后一步。
- 若已有实验行只存纯文字，应通过关联的**同版本**文档快照恢复结构化内容；若必须新增字段／版本化结构，做向后兼容的最小迁移，保留原步骤ID、完成状态、偏差、计时及结果关联。
- 正在执行或已完成的实验不能因Protocol库后续编辑而静默替换内容。使用实验关联的版本／快照，不临时读取最新Protocol来伪装恢复旧步骤。
- 旧记录确实只有纯文字且不存在可核对的同版本富内容时，保留原文，提示“旧记录未保存完整格式”，说明可用的查看来源；不得自动编造表格或拿新版覆盖旧记录。旧数据可恢复与不可恢复数量在报告中区分。
- 新建及可恢复的实验必须完整显示；不能把旧数据例外当作所有表格缺失的豁免。
- 富内容中的实验参数替换须覆盖表格单元格并沿用既有模板规则，不更改原Protocol。未解析的关键参数必须明显可见，不能替换为空白。
- 沿用现有安全渲染与附件权限规则，不能直接插入未经过现有处理的任意HTML；本轮不新造文档格式或另建编辑器。

### 17.3 RUN-12-02：辅助工具同排紧凑展示

手机当前步骤保留一条辅助工具栏，默认顺序为 **计算器｜计时器**，各用图标＋短名称。

- 在320／360／390 CSS px宽度及默认字号下，两项保持同一行，建议两列等宽或内容自适应，间距约8 px；每个触控区域至少44×44 px。
- 使用次要按钮视觉层级，避免两个大卡片分占多行；正文及完成步骤操作保持清晰。
- 工具栏建议置于当前步骤标题之后、正文之前，便于长步骤随时找到工具；本轮不要求新增遮挡正文的浮动栏。
- 计时器入口按需展开时长设置和开始／暂停／继续／重置等现有功能，可采用下方区域或底部面板；**同排要求针对两个入口，不强迫全部计时控件挤在一行。**
- 运行中显示紧凑剩余时间或状态，例如“计时器 04:32”；状态变化不能挤掉计算器入口或遮住正文。必要的详细信息放在展开区域。
- 默认首屏同排；真实200%缩放或大字体时允许适应性换行，保证完整标签、可触控和可滚动，不为同排缩小到难以使用。
- 入口按钮不得误提交Run表单或把当前步骤标为完成。打开、关闭计时面板或计算器不应隐式开始、暂停、重置或新建计时器。
- 切步骤／刷新／去计算器再返回时，依现有计时状态与起止时间恢复；后台经过的时间应计入，不依赖页面前台每秒回调累减来维持准确性。无需新增系统级后台闹钟能力。

### 17.4 RUN-12-03：计算器进入工具主页，并能回到原步骤

1. 从手机Experiment Run的通用“计算器”按钮，单次点击直接进入 Calculator **主页面／工具选择页**，显示常用任务、搜索及全部工具入口。
2. 执行时确认实际主页路由；预期形态为 `/tools/calculator`，不得未经核对新建重复主页。禁止这个通用按钮附带默认 `dilution` 或其他具体工具ID。
3. 即使上次用过稀释或其他工具，从Run的通用入口进入仍先显示主页；现有“恢复上次草稿”可作为用户主动选择，不能自动抢占主页。
4. 与实验相关的 `experimentId`、`experimentStepId`、当前组／步骤及允许的返回目标保留在既有上下文机制中。主页→搜索／常用工具→具体计算→保存／记入实验的全过程不丢关联，不能写到另一个实验或已切换的步骤。
5. 提供清楚的“返回实验”动作。无论选了几个工具，都能直接回到原Run和原选中步骤；同时验证正常浏览器返回顺序。返回目标须使用受控站内路由，不接受任意外部跳转地址。
6. 离开Run前保护未提交的偏差备注、勾选状态与必要的本地表单草稿；返回恢复原步骤、合理的阅读滚动位置、未保存提示及计时状态。不将保存草稿误当作提交步骤完成。
7. 若离线，沿用已经支持的计算器缓存能力及队列。不可用时说明具体状态，仍保留Run草稿和安全返回路径。
8. 此改变针对通用计算器入口；用户在其他位置显式点击“稀释”等特定任务的快捷入口，仍可直达相应任务。
9. 本轮手机行为必须达标；共享组件改动不得破坏桌面侧栏的打开、关闭、键盘操作及上下文关联，不要求重做桌面布局。
