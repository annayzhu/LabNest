# 任务书二：账号工作区下的独立离线 iPhone App 与 Watch 手机同步

日期：2026-10-22。版本：需求确认版 v1.2，尚未实施。沿用 Q1–Q9 的主要功能、个人设备、冲突与附件选择；用户后续已确认账号纳入第一阶段、手机跨隔离 Wi-Fi 使用同一套 LabNest、Watch 默认经手机同步、断网继续记录并恢复后自动补传。旧“先无账号、后账号”交付顺序已被本版替代。

v1.2：离线客户端路线不再预设为原生页面，改在 M0 比较后由用户在决策关卡选定（第 5.2 节，倾向复用 TypeScript）；P1 为单一默认工作区，跨工作区隔离移到按需的 W 阶段；P0 跨网快路见任务书一第 1.4 节。

与[任务书一](./01-device-connection.md)共用账号、工作区、设备和同步实现，不开发两套产品。任务书一负责接入与权限，本任务书负责本地业务、编辑、同步和手表操作；M0–M1 属于共同的第一阶段 P1，M2–M3 完成主要功能扩展 P2。P1 是内部验证阶段，不代替完整第一版。

## 1. 产品目标与完成标准

第一版是一款可独立运行的研究工作 App，不只是“远程打开电脑网页”，也不只是计时器或现场快速记录工具。按照用户要求，第一版覆盖电脑端大部分功能；分批开发仅是实施顺序，不能用其中一批代替整个第一版。

“独立运行”的最低含义：

1. 首次连接可信实例并登录、同步所需内容后，Mac 关机或手机断网，App 仍可启动，不依赖加载远程首页。
2. 已准备的业务数据、文档与指定附件可以读取，支持范围内的修改先安全保存在手机。
3. App 被关闭或系统终止后，再次打开仍能找到这些内容和待同步修改。
4. 恢复连接后自动同步；不丢记录、不重复创建、不把另一端修改静默覆盖。
5. 手机随身时，Watch 默认经手机同步，不要求蜂窝套餐、VPN 或独立登录；电脑断线后不要求离开实验室重新扫码。
6. 手机处于一楼 Wi-Fi、Mac 处于无法直接互访的二楼 Wi-Fi 时，通过已验证的安全跨网通道连接同一实例与工作区。
7. 未来服务器从 Mac 迁到实验室常开机器时，移动端不需要推倒重做。

**首次使用规则（替代旧 Q8 的无账号阶段）：** 全新安装先通过可信连接信息选定这套本地 LabNest，再登录账号并进入获授权工作区；普通掉线不要求每日登录或重配。离线工作以首次授权及准备过的内容为前提，不提供全新手机完全离线建库后再合并另一库的能力。

**Q9 同步范围保留并提前纳入当前账号版：** 登录后自动同步有权限的工作区目录、文档正文与常规结构化记录，大附件按需下载，可选择整个项目离线保存。P1 验证同步机制及核心现场内容，P2 按功能矩阵覆盖全部主要模块；不能把只缓存一个实验作为完整第一版。账号登录不意味着自动发现互联网上未知的自托管实例，也不意味着已下载所有附件。

**P1 共同完成标准：** 已准备实验/规程可断网打开，连续记录步骤、简短文字、测量/小型结果、照片及计时；Watch 可转交步骤和计时操作；手机或手表重启后可恢复，服务可达后自动补传且同一操作只生效一次。更复杂的模块编辑由 M2–M3 完成，不另建一套临时离线存储。

## 2. 已确认条件与本人的判断

| 条件 | 处理原则 |
|---|---|
| 真实数据先本地 | Mac 继续保留 PostgreSQL 与附件；手机保存工作副本和未同步修改，不默认使用公有云或 iCloud 同步 |
| 第一版功能较完整 | 必须建立逐模块功能矩阵；“只能联网点开网页”不能算完成该模块的离线目标 |
| 手机随身、Watch 辅助 | 手机承担主要网络通信和持久接收；Watch 不要求蜂窝套餐；同网也默认经手机同步 |
| 首期 Apple 平台 | 复用现有 SwiftUI 工程作为外壳，页面与业务规则的实现方式由 M0 决策关卡选定；保留未来 Android 可调用的标准 API；不同时重写两套平台 |
| 第一阶段账号 | 首个拥有者与登录在 P0 交付；P1 补齐默认工作区、角色、设备与恢复，实际后端授权覆盖所有入口；不是只预留登录接口 |
| 主要模块离线，复杂导入导出联网 | Q5 已确认；手机联网时仍应有相应入口，不能把在线功能全部推回电脑 |
| 先按个人设备使用 | Q6 保留；首版不做实验现场多人快速轮换，但退出/换账号和队列隔离必须安全 |
| 保留双方修改并核对冲突 | Q7 已确认；只在能够证明互不影响时自动合并，不静默覆盖 |
| 跨 Wi-Fi 使用 | 两网都能上网但不能互访；手机以可信私有通道访问同一 Mac，不把 LAN 发现当作跨网能力 |
| 账号内容同步 | Q9 保留；当前账号版自动同步目录/正文/常规数据，大附件按需，P1→P2 逐模块完成 |

建议继续采用本地优先架构，而不是把现有服务器直接公开到互联网。离线能力能解决实验室断连时继续工作的需求；若要在 Mac 关机时仍实时共享数据，未来仍需要常开的同步服务器。这两件事不能互相替代。

## 3. 第一版功能矩阵（Q5 已确认）

“离线”包括已下载内容的常规查看/编辑，以及在已登记工作区中新建本地记录；不只是只读缓存。未下载附件不能凭空打开，编辑仍遵守现有锁定、版本与必填规则。当前账号版首次需连接可信实例、登录并同步已有工作区。离线数据仍受原账号与工作区约束，不因换网络变成另一份库。

| 模块 | 手机联网时的首版目标 | 离线首版目标 | 仍需联网或另行验收的部分 |
|---|---|---|---|
| Overview／日历 | 今日任务、进行中实验、提醒、跳转 | 本地任务与日历，显示最后更新时间；新增/修改个人提醒 | 其他设备最新改动；后台远程通知 |
| Entries | 清单、搜索、详情、快速记录、完整常规编辑、附件 | 新建/编辑文字、图片、列表、小表格；选择已知关联对象；先记后关联 | 未下载附件、远程 AI 整理 |
| Projects | 清单、筛选、详情、新建/编辑、关联方案与记录 | 新建项目草稿、编辑常规资料、查看和编辑本地关联 | 未下载的完整关系网络、全库统计 |
| Research Plans | 科学前提、设计、材料、计划、关联 Protocol | 常规文档编辑、新建方案草稿、绑定已下载版本 | 未下载规程与远端内容 |
| Protocols | 清单、搜索、规程与版本、富文本、结果模板常规编辑 | 新建/修改草稿；使用已下载规程；保留采用版本不可变规则 | 复杂 DOCX/PDF 解析、正式发布/审批先在线确认 |
| Experiments | 新建、选规程、参数、实验计划、步骤、实际值、偏差、计时 | 基于已下载且满足规则的规程版本创建实验；连续执行多个步骤；追加记录与本地提醒 | 无本地模板的创建；受控完成/锁定需服务端确认 |
| Results | 多结果模板、多 sheet、小表格、附件、当前支持的可视化 | 在同一次实验下填写多份结果；本地测量与表格，保留单位、行标识和来源 | 超大数据表全量分析、服务器任务、未下载原文件 |
| Reports | 清单、关联结果、常规图文报告编辑 | 新建/编辑报告草稿，引用已下载结果与图片，保留来源版本 | 正式导出/打印、复杂图表生成、受控发布 |
| Sequences | 清单、查询、序列、注释、验证状态、关联材料 | 查看/新增/编辑常规序列记录与验证说明，使用同样字母表和坐标规则 | 外部数据库检索、复杂文件批量导入 |
| LabNest 自有 Inventory | 物品、位置、批号、状态、出入库、实验关联 | 查看缓存，登记领用/归还/入库意向及本地备注；显示库存是旧快照 | 真正可用余额与其他人领用，回网后事务核对；不离线保证库存充足 |
| Tools | 工具目录、已有链接、结果关联 | 已明确打包进 App 的本地计算工具可离线，其余展示可用性 | 外接 CNV/qPCR 分析网站或独立服务，不能因出现在目录就宣称可离线 |
| AI | 用户自带服务配置、开关、预览并确认 | 不调用未部署的模型；可保存待整理内容 | 实际模型请求联网且由用户开启，不自动上传全部离线库 |
| 搜索／全局关联 | 搜索整个有权限工作区，显示所在模块并跳转 | 搜索已下载内容与本地新建草稿；明确“仅本机内容” | 不把未下载结果当作不存在；在线结果需重新校验访问权 |
| 账号／设备／同步／设置 | 登录、获授权工作区、连接管理、语言、下载与设备撤销 | 原账号已准备内容、待同步与冲突可用；退出/换账号保护原队列 | 首次登录、重新授权、撤销远端设备与账号管理 |

关于“常规编辑”：不是仅能修改标题。文档至少包括段落/标题、字体与字号、清除格式、列表、检查项、图片、链接、表格、块顺序和撤销恢复；与当前支持的数据结构往返一致。不能在手机保存后丢失未知块、表格内容或规程实验关联。

Q5 已确认复杂导入导出、外接工具和 AI 联网使用，不列为首版必须离线完成的能力。在线能力也应在手机有入口和明确反馈，不是全部要求回电脑完成。已经明确打包在 App 中的本地工具仍可离线，不因 Tools 总入口联网而禁用。移动端首次支持的编辑块清单与暂不支持块的只读保护必须逐项登记。

## 4. 界面与现场操作要求

- 保留紧凑、克制的风格；不新增大面积统计卡片或连接状态看板。
- 首屏展示实际任务和近期内容，不先问十几个字段。快速记录可以不关联实验，保存后补关联。
- 按现有手机设计保留主要底部入口，其余模块在侧栏中；“连接设备”独立可到达。
- 中英文文字、日期、单位与错误信息全覆盖。内部状态枚举不能直接暴露给用户。
- 小屏表格可横向滚动或逐行编辑，固定关键标识；不能通过把字号缩得不可读来塞下电脑表格。
- 重要的本地保存状态就近显示：“已保存到手机”“待同步 3 项”“需要核对 1 项”。不要让用户误把本地保存当作电脑已收到。
- 键盘遮挡、光标、选区、格式工具栏、长按拖动、删除按钮不移动、字体清除、三线表与文档预览属于必测回归。
- 离线未准备的内容显示“未下载，联网后可获取”，不是空白页面或“数据丢失”。
- 日常不出现要求重新输入 IP/扫码的阻断页。首次选定实例、账号认证、工作区可访问、内容同步和附件离线准备分别显示状态。
- 退出或换账号前提示待同步项；取消退出、保留受保护本地副本、重新登录原账号恢复等路径明确，不能默认丢弃。

## 5. 总体架构建议

```text
电脑 Web（二楼）─────────┐
                       ↓
             统一账号/工作区授权＋版本化业务 API
                       ↓
                 PostgreSQL＋附件存储
                       ↑
             固定可信私有 HTTPS 跨网连接
                       ↑
iPhone（一楼）本地库＋文件＋可靠待同步队列
                       ⇅ WatchConnectivity＋持久回执
              Watch 任务快照、计时、操作队列
```

服务器仍是共享记录的确认来源；手机是可以独立工作的本地工作副本，不是另一套互不相干的科研数据库。离线产生的修改在确认前明确标记，恢复连接后经同样规则校验再进入共享记录。

### 5.1 保留与增加的技术

| 部分 | 建议 | 原因及验证要求 |
|---|---|---|
| 服务器 | 保留现有 Next.js、Prisma、PostgreSQL | 不为离线 App 引入微服务、消息总线或更换主数据库 |
| iPhone 外壳 | 保留 SwiftUI 工程 | 已有扫码、通知、Live Activity、Watch 桥接可复用；无论选哪条路线都保留 |
| 本地持久化 | SQLite 系存储，单一数据访问层；由原生持有、供所选客户端调用（路线 A 经受控桥访问） | 必须证明本地业务更新与待提交操作可一起提交、迁移可恢复；不同时引入两套本地库；不依赖可能被系统清理的网页存储作为唯一副本 |
| 页面与业务规则 | **M0 决策关卡选定**：路线 A（App 内打包的 Web 客户端）或路线 B（原生 SwiftUI），见第 5.2 节；相机、计时、通知、Watch 无论哪条路线都由原生负责 | 不依赖远程网页启动；离线业务规则只保留一份实现 |
| 富文本编辑 | 现有编辑器打包为 App 内本地资源，由受控桥读写本地结构化文档（两条路线都需要） | 避免重写全部科研文档语义；这不是加载 Mac 的远程页面 |
| 网络 | 任务书一的可信私有 HTTPS＋版本化 API、附件传输 | 不依赖同 Wi-Fi；不把原生 App 绑在 Next Server Action 内部格式；跨网通道需两端实测 |
| 账号授权 | 复用 P1 账号、成员关系和会话 | 手机不另建独立账号库，Watch 不持有手机长期刷新凭据 |
| Watch | 保留 SwiftUI，改为手机辅助同步 | 不要求 Watch 继承手机 VPN 路由；手机可离线保存 Watch 操作 |
| Android 预留 | 协议、稳定 ID、能力清单、测试样例不绑定 Swift 对象 | 未来 Android 可使用同一服务器，而非现在同时开发 |

本地 WKWebView 可由自定义资源加载机制提供 App 内资源，但编辑器必须通过离线启动、文件访问、图片、IME、粘贴和往返保存验证；不能假定整个带 Server Components 的 Next.js 网站可以直接复制进 App。[Apple WKURLSchemeHandler](https://developer.apple.com/documentation/webkit/wkurlschemehandler)

### 5.2 离线客户端路线：M0 比较，决策关卡选定

完整首版要求离线新建实验、按体系解析参数、遵守规程版本规则、填写结果模板。这些规则现在都在 TypeScript：[structured-protocol.ts](../../../src/lib/structured-protocol.ts)、[protocol-document.ts](../../../src/lib/protocol-document.ts)、[run-step-content.ts](../../../src/lib/run-step-content.ts)、[structured-run.ts](../../../src/lib/structured-run.ts) 与计算器引擎，并有公开测试（如 [structured-protocol.test.ts:69](../../../src/lib/structured-protocol.test.ts:69) 的 350/600 µL→50/80 µL）。离线时这些规则必须在手机上运行，因此路线选择决定了规则是一份还是两份。

| | 路线 A：App 内打包的 Web 客户端 | 路线 B：原生 SwiftUI |
|---|---|---|
| 页面 | 复用现有 React 组件，改为从本地数据层取数，由 App 内资源加载，不加载远程页面 | 为各模块重写原生页面 |
| 业务规则 | 共享 `src/lib` 的 TypeScript 规则，服务器与手机同一份代码、同一组测试 | 在 Swift 中重写，或另行设计共享方式 |
| Swift 负责 | 本地库与文件（经受控桥）、相机、计时、通知、Live Activity、Watch | 全部 |
| 主要风险 | 现有页面依赖 Server Components 与 Server Actions，需要改出客户端数据层；WebView 内的性能、键盘与 IME；打包与版本对应 | 两套规则与两套界面长期并行，正是第 16 节所列风险；首版覆盖“大部分功能”的工作量最大 |

**判定用例（两条路线做同一组，用合成数据）：**

1. 飞行模式下，用已下载的规程新建实验并按体系解析参数，结果与 `structured-protocol.test.ts` 的期望一致（350/600 µL→50/80 µL）。
2. 复杂现有文档离线编辑往返：段落、表格、图片、未知块、单位与链接不损失（同 M02）。
3. 记录保存后强制结束并重启，本地库与待同步队列完好（同 M01）；本地数据不放在可能被系统清理的网页存储里作为唯一副本。
4. 在最低支持的 iPhone 上，用建议规模的数据测启动、滚动、保存时间。
5. 规则共享：说明服务器与手机如何使用同一版本的规则代码与测试，以及版本不一致时如何阻止写入。
6. 工作量：按功能矩阵估算各模块在该路线下的改动量。

**当前倾向 A**：它让离线规则只有一份，与 PRODUCT.md 的“一处权威实现、多处适配”一致，也能复用已上线的手机交互（`3b9ae16b` 的底部栏、侧栏、··· 面板、键盘工具栏与长按拖动）。若判定用例证明 A 在性能、存储可靠性或键盘上不可接受，再选 B 或混合方案（例如列表原生、编辑与规则在 Web）。路线由用户在 M0 决策关卡决定；不能未经讨论直接全量迁移 React Native/Flutter。

## 6. 本地数据与下载设计

### 6.1 本地必须持久保存的内容

| 内容 | 必需信息 |
|---|---|
| 工作区连接资料 | serverId、userId、workspaceId、可信端点、设备关联、协议版本；秘密凭据单独放 Keychain |
| 已下载业务记录 | 原 ID、类型、版本、关系、下载状态、服务器更新时间 |
| 本地草稿和修改 | 本地稳定 ID、原始版本、修改内容、设备创建时间、当前状态 |
| 待同步操作 | clientMutationId、原账号/工作区、原设备、动作类型、依赖、payload schema、尝试次数、最后错误 |
| 同步回执 | 操作 ID、服务器记录 ID、确认版本、收讫时间；供重试和排错 |
| 附件清单 | 文件 ID、哈希、大小、类型、本地路径、下载/上传/校验状态 |
| 冲突资料 | 基础版本、本地版本、服务器版本、来源设备、处理选择 |
| 计时 | 计时 ID、实验/步骤、状态、持续时间或截止时刻、revision、本地通知标识 |

以上从 P1 起按稳定 serverId/userId/workspaceId 隔离，不能按 IP 或 Wi-Fi 名称作为唯一目录名。切换用户不能把前一个人的队列放到新用户身份下提交；Watch 消息也携带并验证对应人员/工作区上下文。

### 6.2 下载不是复制整个服务器

- 登录后自动分页同步有权访问的工作区目录、正文和常规结构化内容；首阶段先验通核心实体，完整首版覆盖功能矩阵。按第 11.4 节显示进度，不能只有手动选择一个实验的缓存。
- Project、Experiment 或指定文档的“供离线使用”用于补齐该范围的必要附件与完整依赖；进行中的实验可自动准备。此操作不等于复制全库大文件。
- 下载该对象的必要关系：所用规程版本、当前模板、执行步骤、相关小型结果、引用的图片等。
- 展示估计体积、已完成项、缺少附件和最后更新时间。只有所选清单全部校验通过才标“准备完成”。
- 大视频、仪器原始数据、超大表格默认只下载元数据/可用预览；完整文件由用户明确选择。
- 删除缓存不能删除未同步草稿、文件或冲突副本。清理前保护被待同步操作引用的对象。
- 下载中断继续或明确重试，不能覆盖此前可用的完整快照；新一代准备成功后再切换。
- 下载范围变化需要区分“本地移除缓存”和“服务器删除业务记录”，两者不能共用一个删除按钮。

### 6.3 新建对象和显示编号

离线创建 Project→Research Plan→Experiment→Result 的关系必须成立。先分配不会碰撞的客户端标识，服务器接受后返回正式 ID/编号与映射；或在现有兼容规则允许时直接采用稳定客户端 ID。实施前检查现有 ID 校验，不批量改写历史 ID。

不能在手机自行递增 PRT/EXP 显示编号后当成全局唯一。待同步期间显示“本地草稿”或唯一临时编号，正式编号回执后更新关联，不生成重复实验。

## 7. 同步契约与事务规则

### 7.1 最小写操作信封

每个写操作至少携带协议版本、`clientMutationId`、`workspaceId`、设备标识、实体标识、动作类型、payload 版本、基础 revision、设备记录时间和依赖操作 ID。

操作者身份和工作区权限由服务器从有效账号会话与成员关系解析；再校验来源设备/Watch 与该主体的关系，不能信任客户端随意填的 userId。时间保留设备发生时间与服务器收讫时间，不能按手机时钟判断谁有权覆盖谁。

### 7.2 本地保存

1. 校验本地必需字段，保留不完整内容作为草稿而不是静默丢弃。
2. 在同一持久化事务内写入业务本地视图及对应操作。
3. 事务完成后才能显示“已保存到手机”。图片等文件采用暂存、校验、登记的可恢复流程。
4. App 被终止后，从本地库恢复；`sending` 状态不能永久卡住，重试沿用同一 mutation ID。

### 7.3 上传与回执

1. 确认当前授权、协议和目标实例；只向可信端点发送。待同步操作的原主体必须与会话一致；已撤销权限不允许自动换账号提交。
2. 按依赖先提交父对象、再提交关联对象或需要其回执的操作；一个冲突不阻塞不相关的项目。
3. 服务端在事务中完成幂等判断、权限/版本/业务规则检查、业务写入、审计与变化记录。
4. 同一 mutation ID＋相同请求返回相同结果；同一 ID 携带不同内容应拒绝，不能当成另一项修改。
5. 收到回执后本地原子更新实体版本、ID 映射和操作状态。未持久化回执不能删除唯一一份本地修改。
6. “服务器成功、网络回复丢失”再次提交时只出现一份记录。幂等键在实例、工作区、原始来源和操作 ID 范围内明确约束；不同账号不可获取彼此回执。
7. 同一原始 Watch 操作通过手机重试、App 重启或受控旧链路迁移后，仍保留同一操作 ID，不因转发创建新业务动作。

不能假定当前八种 Web 队列操作都已有完整幂等保证。逐路由核对，尤其没有携带 mutation ID 的旧调用必须补齐或适配。

### 7.4 下拉更新

- 采用工作区范围的分页变化游标，不对所有业务表反复全量拉取。
- 初始下载需有一致的快照标识/高水位；下载期间服务器发生的修改通过后续变化补齐，不能出现时间缝隙。
- 保留删除标记和撤销访问的信息；不能只拉新记录而永远保留服务器已删除内容。
- 游标保存与本地落库同事务，避免落库一半却推进游标。
- 游标过旧时重新构建已选下载范围，仍保护未同步修改和冲突材料。
- 电脑端 Server Actions 和 API 写入也必须进入同一版本与变化记录机制；只给手机 API 加变更日志会漏掉电脑编辑。

### 7.5 触发和状态

- 前台启动、网络恢复、Wi-Fi/蜂窝切换后重新可达、回前台、手动同步、当前页面保存后均可触发；同一账号/工作区采用一个协调入口，避免并发同步互相覆盖。
- 能上互联网不等于能访问 LabNest。先检查已受信实例及有效会话，再同步；网络超时/私有连接关闭不删除会话，401 正规续期，403 停止越权提交，409 进入核对。
- 普通掉线期间继续本地记录；恢复后自动发送。重试采用有上限的退避并在重新可达时及时唤起，不让用户回电脑旁重新配对。
- 前台恢复应自动完成一轮同步；后台作为尽力补充，不用无限后台循环或秒级轮询冒充可靠同步。
- iOS 的后台调度由系统决定，文件传输采用适合的系统机制；用户强制退出后也不得承诺后台一定补传。[Apple 后台策略](https://developer.apple.com/documentation/BackgroundTasks/choosing-background-strategies-for-your-app)
- 建议状态：仅本地草稿、待同步、提交中、已同步、待核对、等待重新授权、输入需修正。网络错误、授权失败和业务冲突不能都叫 conflict。

### 7.6 拟议服务接口

| 接口组 | 目的 |
|---|---|
| `GET /api/v1/capabilities` | 协议版本、支持的实体/操作、附件限制与功能可用性 |
| `POST /api/v1/sync/prepare` | 选定下载范围的对象/版本/附件清单及起始游标 |
| `GET /api/v1/sync/changes` | 按游标与权限分页取得变化/删除标记 |
| `POST /api/v1/sync/mutations` | 小批次提交；返回逐项回执、可重试错误和冲突 |
| `GET /api/v1/sync/receipts` | 回执丢失后的恢复核对；不重复业务操作 |
| 附件创建/分块/完成/读取接口 | 中断恢复、哈希验证、访问校验；未完成文件不显示为已同步 |

这是拟议协议，不要求把所有现有接口一次性改名；适配层复用现有业务服务。批次可以逐项成功，但单个科研操作不能出现一半业务成功、一半审计失败的状态。

## 8. 冲突规则（Q7 已确认）

基本规则：能证明是独立追加的记录可合并；覆盖相同信息必须比较版本；科研事实不能用“最后一次上传获胜”静默替换。

| 情况 | 推荐处理 |
|---|---|
| 两端分别新增 Entry/测量 | 不同 mutation ID 保留两份；回执重试同一操作则去重 |
| 两端改同一文档的不同块 | 只在稳定块 ID、共同基础版本和无依赖冲突时三方合并；否则进入核对 |
| 两端改同一段文字、同一单元格 | 保留基础/本地/服务器三份，用户逐项选择或另存草稿 |
| 草稿 Protocol 已在电脑正式采用 | 不能覆盖已采用版本；手机修改另存关联草稿版本 |
| 实验执行计划在电脑改变 | 保留手机当时的执行快照、步骤 ID、实际记录；人工核对是否能映射，不换 revision 强行重发 |
| 手机完成步骤，电脑把同一步骤跳过 | 保留两项意图与原因，交用户核对，不以时钟先后消除一方 |
| 两端同时操作计时器 | 每次操作有计时 ID 和 revision；顺序可解释，否则提示核对，避免复活已取消计时 |
| 两端领用最后一份库存 | 服务端事务校验；冲突保留真实领用记录待处理，不能简单丢弃或默认负库存 |
| 电脑删除文档、手机仍在编辑 | 服务器删除不被自动复活；允许查看、导出或另存本地草稿 |
| 人员/设备权限被撤销 | 停止提交，保留未同步资料的处理说明；不能自动换成其他身份重试 |

不在首版引入全系统 CRDT 或多人实时共同编辑。离线并行修改和实时协同不是同一需求，先用版本、稳定块 ID 和明确冲突核对完成可靠性。

## 9. 附件、表格与结果的专项要求

### 9.1 附件

- 保存原始文件、大小、哈希和来源；缩略图/压缩预览另存，不能用压缩图片替代唯一原图。
- 拍照成功后先写入受保护的持久目录，不只留临时路径；上传前后校验内容一致。
- 大文件分段与续传是否启用由实际大小限制决定；必须覆盖中断恢复，不硬编码所有文件一次传完。
- 记录和附件可以分别同步，但页面明确显示缺少的附件，不能显示整条记录已完整同步。
- 未同步文件不能被系统缓存清理策略或用户“清理已下载内容”误删。

### 9.2 大表格

- 手机显示元数据、筛选结果、虚拟化小视窗；不要把整个十万行文件变成一个富文本表格。
- 小型结果表继续使用结构化列/行标识；大数据集保留原文件和可查询视图，下载所选范围。
- 离线编辑局部行时，以行/单元格 ID 和版本提交，不把本地截取部分覆盖成完整数据集。
- 未下载的部分清楚提示；统计图标明基于全量还是本地子集，避免科研解释错误。

### 9.3 多模板结果与可追踪性

- 同一次 Experiment 的多个 ResultTemplate 对应多个结果集合，保留共同 experimentId 和独立模板/数据版本。
- 单位、样本编号、时间点、重复类型、原始值和展示值分别保留；同步不能把同名但不同样本的行合并。
- 离线分析与图表记录所用输入快照和参数；回网后数据变化不偷偷重算并替换原解释。
- ProvenNest 仍是独立系统。若 Inventory 实际来自外部连接，离线只承诺已定义的缓存或待发送请求，不直接操作另一系统数据库，也不复制全部样本库。

## 10. Watch 辅助端：默认通过随身手机

默认链路固定为 Watch→iPhone→LabNest；即使同一 Wi-Fi 也优先这一条。Watch 无需蜂窝套餐、VPN、服务器地址或独立账号登录。现有同网直连只作受保护的旧版兼容，不在首阶段增加双通道竞速或自动双写；切换链路必须保护原操作 ID。

### 10.1 首版功能

- 当前实验/当前步骤与必要操作提示。
- 查看、开始、暂停、继续、结束支持的计时；到时提醒与手动完成步骤分开。
- 确认步骤、记录跳过原因或简短状态，必要时提示到手机填写详细内容。
- 显示“已传给手机”“待传给手机”“已同步电脑”的区别。
- 不做完整富文本、复杂表格、项目管理、照片管理或独立登录。

### 10.2 数据与通信

1. iPhone 从自己的本地库形成小型任务快照，连 Mac 失败也能提供已准备内容。
2. 最新显示状态可以用 application context；用户每一次操作必须使用耐久队列与唯一操作 ID。
3. `sendMessage` 适合双方当时可达的即时反馈，排队传输用于暂不可达时交付；发送方不能在未收到应用级持久接收回执前删除唯一副本。[Apple WCSession](https://developer.apple.com/documentation/watchconnectivity/wcsession)
4. Watch 操作写本地后发给 iPhone；iPhone 在持久化事务完成后回“手机已保存”，最终服务器回执再单独更新状态。
5. 手机保留原始 Watch deviceId 和 mutation ID；转发不能制造新 ID，重试不能变成第二次完成/领用。
6. Watch 操作必须通过其合法 parentPhone、人员和工作区关联校验，不接受任意手机伪造来源。人员由服务器验证手机会话获得；手机不得把上一账号的 Watch 消息改成当前账号提交。
7. 短暂失去手机时，手表保留已见任务和待转交操作；不把旧的一条 pending 限制带入新队列。
8. 手机长时间不可达或换绑有未处理操作时，优先保留资料并说明状态，不默默清空。
9. 手机退出、切换账号或已获知撤销权限后，Watch 锁定原账号业务界面，保留受保护未同步资料；重新授权前不能把旧实验交给新账号继续操作。
10. P1 就实现这条耐久转交链路，不能以“配对码转发成功”代替业务同步。手机后台或锁屏的传输时机遵守系统限制；后台不能立即交付时留队列，前台恢复自动重试。

用户选择的是手机辅助模式，因此不要求手表在完全没有手机时完成整个实验流程。但短时连接抖动不应丢动作，也不应让已开始的本地计时消失。

`transferUserInfo` 的真实传输必须在已配对真机测试，模拟器不能替代。[Apple 传输要求](https://developer.apple.com/documentation/watchconnectivity/wcsession/transferuserinfo(_:))

### 10.3 双端提醒

- 同一个 timerId 在手机和手表具有共同状态与 revision，明确哪一端负责提示、另一端如何避免不必要的重复。
- 手机的锁屏计时/Live Activity 是展示与提醒，不是后台永远运行的计时线程。
- 用持久化截止时间与状态重建倒计时，不用网页组件里每秒减一的内存数值作为唯一事实。
- 区分持续时长和日历时间提醒；记录时区信息，测试手动改时钟、夏令时、重启与长时间后台。
- 本地通知由系统处理，须尊重权限、专注模式和系统调度，不承诺实验级绝对准点。[Apple 本地通知](https://developer.apple.com/documentation/usernotifications/scheduling-a-notification-locally-from-your-app)
- 一端取消计时、另一端离线时，不能承诺另一端马上撤销提醒；恢复联系后优先同步取消。提醒到时不自动记为完成实验步骤。

## 11. 第一阶段账号接入、离线身份与后续服务器迁移

账号已纳入 P1，具体初始化、认证、权限与设备管理由任务书一第 3、6 节负责。本文件不另建认证体系；这里定义移动端消费这些能力的方式。原 v1.0 的“后续账号 A01–A06”不再单列为延期工程，其工作已纳入下表。

| 原账号工作包 | 当前归属 | 交付阶段 |
|---|---|---|
| A01 登录/成员关系/会话 | D03–D05；移动端接入 M05 | P1 |
| A02 工作区发现/可信实例 | D02、D06、D08；M05 | P1，首次仍需受信实例信息 |
| A03 自动内容同步 | D13、M06–M09，再扩展 M11–M18 | P1 核心机制；P2 全部主要模块 |
| A04 附件按需/项目离线 | M06、M08、M11/M15、D13 | P1 核心图片/附件；P2 完整项目 |
| A05 旧匿名资料与队列升级 | D03、D10、M21 | 首次升级前完成，P2 扩展回归 |
| A06 退出/换账号/撤销 | D04–D06、M05/M08/M10、M22 | P1 实施，P2 全模块回归 |

### 11.1 P1 必须使用真实账号上下文

- 统一 RequestContext 解析人员、成员关系、工作区、设备及允许操作；电脑、手机和 Watch 转发复用同一服务端入口。
- 首个拥有者与默认工作区初始化在受保护的本机管理流程完成，不能由任意远端访问者抢占。
- 全部旧、新数据入口都需授权，包括搜索、导出、图片/附件、后台任务、同步及旧 Watch 路由；主页面要求登录但 API 裸露不算完成。
- 本地秘密凭据使用系统安全存储；文件按账号隔离，说明设备数据保护、缓存清理和系统备份策略。初始同步不下发服务端数据库/AI 供应商等秘密。
- P1 只有一个拥有者和一个默认工作区；角色在写操作上检查，用同一工作区的只读测试账号验证。跨工作区隔离与测试在按需的 W 阶段（任务书一第 3.5 节）。首版不做公开注册、多机构托管或共享设备快速轮换。
- 账号身份与设备来源分别记账，历史匿名记录不追认为新管理员亲自完成。

### 11.2 离线身份、退出、撤销与恢复

| 情形 | 手机/Watch 行为 | 服务端同步行为 |
|---|---|---|
| 普通断网、切换 Wi-Fi、Mac 休眠 | 保持当前账号关联，已准备内容可用，操作本地保存 | 自动等待/重试，不要求重新配对 |
| 短期访问会话到期 | 不清空本地记录；按已定义离线授权策略继续或锁定 | 正规续期；确需登录时暂停同步并提示 |
| 用户主动退出 | 锁定该用户本地内容与 Watch 展示；提示待同步项，保留受保护恢复路径 | 停止其队列发送并撤销相应会话 |
| 登录另一个账号 | 独立本地分区，不自动显示或提交前一账号记录 | 使用新账号成员权，不能改写旧操作作者 |
| 已收到账号禁用/成员移除/设备撤销 | 停止相关业务访问和新业务操作，保留受控恢复材料 | 拒绝提交，不自动重试或换身份 |
| 完全离线、尚未获知远端撤销 | 只能按上次可信授权与本地策略运行 | 下次连接以当前权限为准；不承诺离线即时收回数据 |

离线授权有效策略需在 D04/M05 冻结并测试；不能用短期网络访问 token 的到期时间简单等同“清空手机”。使用系统设备锁保护离线资料；不会因为离线就允许全新账号首次登录。

已撤销用户的未同步材料由有权人员依恢复流程核对，保留原始来源及导入审计；不得为了补传成功替换成管理员署名。用户不应通过重新扫码规避撤销。

### 11.3 手机跨 Wi-Fi、未来迁到常开服务器

- 当前 Mac 与 iPhone 通过任务书一的可信私有 HTTPS 相连。两端网络登录与 LabNest 人员登录不同，Watch 不需要单独加入私有网络。
- 当前数据继续保存在 Mac，手机为受保护工作副本。Mac 关机期间可离线记录，但无法取得尚在 Mac 上的最新内容。
- 未来常开服务器可以在实验室部署，不默认采用公有云。搬迁需保留工作区/业务 ID、文件哈希、审计、幂等回执和变化记录。
- 暂停旧服务器写入后备份与核对，再切换；不能运行两个接受写入的“主服务器”而没有一致性方案。
- 新安装身份或证书通过明确迁移授权建立信任，不是简单改 IP。游标过期可重新同步，但本地未提交操作及原 mutation ID 必须保留。
- 当前不建设托管账号目录、跨地域数据库、Kubernetes、公有云订阅或全新手机离线建库合并。

### 11.4 当前账号版的同步体验（保留 Q9）

1. 通过受信连接信息确认自托管实例，再登录，获取获授权工作区；一个直接进入、多个选择、零个说明无访问权。
2. 此后打开 App 或换 Wi-Fi，不重复扫码或查 IP。首次没有任何实例信息时，不能仅凭用户名猜测全球服务器位置。
3. 自动分页同步完整有权业务目录、正文、常规结构化数据与关系，展示进度与最后成功时间。P1 支持核心实体，P2 按功能矩阵补齐；未支持的实体不得静默计为全部完成。
4. “工作区全部内容”不包含其他工作区、其他成员私有记录、系统密钥或所有文件字节。服务器按成员权过滤，客户端不能先下载后隐藏。
5. 图片、视频和仪器原文件按需下载；必要预览可缓存，完整文件有下载状态。用户选择整个项目离线时，确认体积、完整依赖与空间，准备后逐项校验。
6. 大型结果集同步描述、索引和查询入口；完整巨型表不装入富文本/手机内存，按第 9.2 节下载可编辑子集或选定原文件。
7. 同步/下载中断、空间不足、权限改变时显示具体未完成项。未校验完的项目不能标“离线准备完成”。
8. 新手机登录同一受信实例可恢复服务器已确认的数据；旧手机从未上传的草稿不能凭登录在新设备出现。
9. 服务不可达时已有授权设备使用本地内容；全新手机不能在 Mac 关机时完成首次登录和获取未下载数据。

登录成功、工作区可访问、内容已同步、附件离线就绪是四个独立状态，必须分开显示。

### 11.5 现有无账号数据升级（一次性迁移，不再另做试用产品）

- 复用已有稳定工作区身份；若旧版尚无 workspaceId，只建立一次默认工作区并保存映射，不复制成第二份同名库。
- 保留业务 ID、编号、关联、版本、文件哈希、设备来源和同步回执；迁移操作者与旧记录实际作者分别保存。
- 验证原本机管理权后建立拥有者，手机须在可信实例真实登录；旧设备 token 不自动升级为账号级全库凭据。
- 升级前清点每台设备待同步记录，并选择受保护回传/导出迁移。不能关闭旧服务后才发现队列被锁在旧 Web origin。
- 已进入新账号库的旧操作仍保存原来源，必要时以明确的迁移类型导入并审计；不把所有旧离线操作伪造成登录用户所做。
- 失败保持原数据完整，回到受保护恢复或只读状态；不能回退成公网/局域网无鉴权写入。
- 账号归属建立不触发云端上传；同时搬服务器时另按第 11.3 节操作。

## 12. 旧版本兼容与迁移

1. 建立现有 Web IndexedDB、显式离线页面、Watch snapshot/pending 的格式清单，记录版本。
2. 在旧 origin 仍可访问时，由受控桥提取并校验未同步操作、文件及依赖；不能直接绕过浏览器存储隔离读取任意来源。
3. 写入新本地库后逐项核对数量、ID、哈希和来源；完成持久化回执前保留旧副本。
4. 如果旧地址不可达且系统不允许读旧 WebView 存储，给出保留旧配置、恢复该地址或用户导出的方法，不建议清缓存重装。
5. 旧 Watch pending 先回传或可恢复导出，不能因从直连改为手机中转而遗漏。
6. 服务端保留一个明确的兼容期；新旧 App 的并存要经过幂等与版本测试。无法兼容则阻止不安全写入并清楚提示升级。
7. 迁移失败使用经过验证的受保护恢复或只读模式，不回滚已经确认的科研记录，也不重新开放旧匿名写入；数据库迁移优先加法，清理旧结构另列任务。

| M-AC29 | 只读成员、篡改附件/游标/回执/对象 ID（两个工作区的部分在 W 阶段） | 服务器按真实身份与角色拒绝越权；缓存清单不提前泄露无权资料 |
| M-AC30 | 手机/Watch 操作已落库但手机回执或服务器回执分别丢失 | 逐级恢复确认，不丢动作、不重复提交；状态不混同 |
| M-AC31 | 新手机登录、部分下载、空间不足、项目离线准备 | 有权目录/正文自动同步；大附件按需，完整准备才标就绪；旧机未上传数据不凭空恢复 |

P1 至少执行 M-AC01–03、05–06、08、11–14、17–21、25–31，限核心现场实体；P2 按整个功能矩阵执行全部 M-AC01–31 和 D-AC01–32。测试“自动”时分别记录前台可达恢复与后台系统调度，不把后台未知时延伪报成即时同步。

建议性能样本包括 1,000 条本地文档索引、100 个已准备实验、10,000 条小型结构化结果行以及大量待同步操作；首轮先测实际最低支持 iPhone 的启动、滚动、保存和存储占用，再冻结指标。不以这些测试规模推断可镜像百万样本库。

## 15. 交付物与发布核对

第一版必须同时交付：

1. 可安装且版本明确的 iPhone、Watch App；说明最低系统要求和安装/签名方式。
2. 对应账号/成员/设备授权、服务端 API、数据库加法迁移及兼容说明。
3. 业务 schema、同步契约、错误码、能力清单及合成请求/回执测试样例。
4. 可信实例接入、账号登录/恢复、跨 Wi-Fi 配置、离线准备、同步核对、冲突解决、附件恢复和设备切换说明。
5. 从当前版本升级、旧队列保护、备份与回退的操作记录。
6. 自动测试、真实 iPhone/Watch 验收证据和剩余限制；不能用 Xcode 编译成功替代。
7. 功能矩阵完成表，明确哪些是已完成、需联网、待开发；不能用“手机端已上线”掩盖主要模块缺失。

原生 App 不会因为 Docker 更新而更新。发布时分别核对 GitHub/开发目录/运行服务源码版本，以及手机和手表实际安装的 build 与协议版本；遵守仓库 AGENTS 的发布流程，保留其他会话改动。

## 16. 计划风险与停止条件

| 风险 | 处理 |
|---|---|
| 完整功能范围被低估 | 先冻结功能矩阵；按 M0 结果估算，不将现场 MVP 偷换成第一版 |
| 远程 WebView 被当成独立 App | 飞行模式＋终止重启作为硬验收 |
| 共用一套 UI 却有两套业务规则 | 业务规则服务端统一；本地校验与官方样例一致，回网仍校验 |
| 登录界面被当作完整权限系统 | 账号在 P1 实施，旧/新 API、附件、搜索和导出逐项授权；不自动开放公网 |
| 两网可上网被当作必然可互联 | 先验通机构允许的私有通道；连接受阻时保留离线，不绕过策略 |
| 手机转交配对码被当作业务转发 | P1 验证真实步骤/计时、持久回执与待同步队列；Watch 无蜂窝也必须通过 |
| 离线库存与实验版本产生冲突 | 不静默丢操作；明确待核对，并保存当时快照 |
| 太早上复杂同步平台 | 先用现有 PostgreSQL、版本与事务变更记录；没有证据不引入消息平台或全系统事件溯源 |
| 本地资源编辑器不可行 | M02 提供失败证据和替代方案，先共同决定再更换技术路线 |
| 离线规则在 Swift 重写，形成两套规则 | M0R 判定用例比较；倾向路线 A 共享 TypeScript 规则；选 B 必须给出规则共享或一致性测试方案 |
| 路线未定就开写 P1 业务代码 | M0 决策关卡前只做 P0 与技术验证 |
| 只做 P0 被当成手机端完成 | P0 只解决跨网与登录；本地库、离线补传与手表转交属于 P1，验收分开 |
| 系统后台/网络能力不受 App 控制 | 前台恢复为可靠路径；通知和后台传输按系统约束验收 |
