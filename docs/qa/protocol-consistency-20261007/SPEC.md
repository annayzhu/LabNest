# LabNest 修改任务书：实验规程转实验的步骤识别、内容重复与模板兼容性

日期：2026-10-07  
版本：v1.0  
执行对象：负责 LabNest 本机代码与调试环境的 Codex  
性质：此前调试完成后新增的独立任务，不表示此前所有任务需要重新执行。

与此前富文本专项的关系：涉及相同编辑器或内容转换时复用其修复，但本次单独验收“规程转实验”的结构与进度，不重新纳入无关历史问题。

## 1. 本次要解决什么

用户反馈：同一份 Protocol（实验规程）在编辑与规程预览时，步骤和说明尚能按层级阅读；创建实验后，实验预览和执行界面出现大量额外 checkbox，把说明段落也拆成了执行步骤。同时，执行界面的步骤标题与正文重复。

请实际排查并修复从“模板／文档导入 → 规程编辑与保存 → 从规程创建实验 → 实验预览 → 执行与进度保存”的整个过程，并逐份检查其他现有规程。不要只调整截图对应页面的样式，也不要只修复这一份 TRIzol 规程。

核心目标：**一个明确的实验操作对应一个执行步骤；说明、用量表和计算依据保留在合适的位置；实验预览与执行使用一致的步骤结构；模板能被系统稳定识别并与相关功能正确衔接。**

本任务书已核对用户提供的三张截图。尚未读取本次运行实例的数据库或源码，也未实测创建与执行流程。下文的根因方向均为待核查项；不得在实施报告中把它们写成已经证实的原因。

## 3. 先定位数据在哪一环变错

先阅读仓库内适用的开发约定，确认启动目录、当前提交和用户实际运行入口。保留原始规程与受影响实验的只读备份，在测试环境复现，避免排查时改动真实实验进度。

对上述规程建立一份逐块对照：

| 对照项 | 需要记录的内容 |
|---|---|
| 来源文档与导入结果 | 若原 DOCX 可用，比较其标题、列表、表格、段落与导入结果；不可用则明确注明。 |
| 规程保存内容 | 实际存在的节点类型、段落归属、步骤标识、标题与正文，以及来源版本。 |
| 创建实验时的转换结果 | 每个生成步骤来自哪个源块；哪些说明被拆开；表格与图片被附到哪里。 |
| 实验保存内容 | 标题、正文、步骤顺序、标识与初始完成状态是否已经错误。 |
| 实验预览与执行 | 两个界面是否重复解析，是否使用不同规则，是否二次包裹 checkbox。 |
| 进度与关联功能 | 勾选、备注、计时器、计算器和附件绑定的是稳定步骤标识还是页面序号。 |

优先核查以下方向，但必须用实际代码与数据确认：

- 将每个段落、每个列表节点或每个换行误当作新步骤。
- DOCX 导入后列表的标题和说明分离，创建实验时未恢复其归属关系。
- 原本存在的结构化步骤与富文本解析结果被同时追加，导致重复。
- 创建过程重复触发、保存重试或打开预览时再次追加步骤。
- 为缺少标题的步骤使用整段正文作为标题，同时保留相同正文。
- 在已有任务列表上再次生成执行 checkbox，形成双层或额外勾选项。
- 切换编辑／预览、保存再打开时，内容格式转换使节点结构持续变化。

输出“问题发生环节 → 证据 → 修复位置”，不要用未经验证的推测代替定位。

## 4. 步骤识别与内容归属规则

### 4.1 按内容用途分类

优先使用项目已有的结构化步骤能力，补齐缺失的约束；不要为了本次修复另建一套与现有系统并行的步骤体系。

| 内容类型 | 推荐呈现方式 | 是否生成独立执行步骤／计入进度 |
|---|---|---|
| 明确的实验操作，如“实验前准备与样本登记”“去培养液并原位裂解”“分管并完成裂解” | 步骤标题＋完整操作内容 | 是，每个明确操作一次。 |
| 操作下的多个段落、普通编号子项或要点 | 保留在对应步骤正文内 | 默认否；只有作者明确设置为独立操作时才拆分。 |
| 用量对照、规格选择、适用于全流程的配比基准 | 准备资料／用量参考，放在第一个操作之前或合适的公共资料位置 | 否。 |
| 某一步专用的表格、图片、计算说明 | 保留在对应步骤内 | 否；表格行、图片、图注不各自生成步骤。 |
| 依据、参考文献、方法说明 | 公共说明或所属步骤的补充说明 | 否。 |
| 操作必需的参数、限制和注意事项 | 就近保留在操作正文，关键内容默认可见 | 不额外计步，也不能为了精简而隐藏或删除。 |
| 人工添加的检查清单 | 保持原清单语义；仅明确指定为执行步骤的条目才进入主进度 | 不默认把任意 checklist 转成主步骤。 |

不应仅依据某些中文关键词来识别资料段落，也不应仅凭标题字号、`H2/H3`、加粗或 checkbox 形状推断操作。应以明确的数据结构和作者设定为主，兼容旧格式时才使用受约束的解析规则。

如果系统确实支持需要逐项勾选的子步骤，明确其与主步骤完成状态的关系；主进度不得同时累计父步骤和子步骤而造成重复计数。本次不要为此额外增加一套用户不需要的复杂功能。

### 4.2 旧文档与歧义内容

- 有明确步骤结构：直接沿用，不再从显示文字重新猜测。
- 只有可识别的旧标题／列表结构：按章节边界和列表层级组织，保留全部内容，并记录源块对应关系。
- 无法可靠确定步骤边界：保留原文，在导入或创建前的步骤预览中清楚标出需要整理的部分，允许人工合并、拆分或标为说明。
- 不得把不确定的段落全部转成 checkbox，也不得悄悄删掉无法解析的内容。
- 人工确认后的归属应保存下来；后续每次创建实验不应重新按另一套规则猜测。
- 如果全文只有资料、没有可执行操作，不自动拼造步骤，也不因分母为零显示“已完成”。应提示整理为可执行规程，或沿用系统已有的纯文档记录流程。

创建前预览是为了核对真正的操作步骤，不要求给所有正常规程增加多层确认页面。优先复用现有创建流程；结构明确且已验证的规程应保持快捷创建。

### 4.3 步骤身份与版本

按项目现有字段实现以下概念，不强制采用新的字段名称：稳定的规程步骤标识、独立的实验步骤实例标识、来源规程与版本、顺序、标题、富文本正文、关联工具或附件。

- 页面上的“步骤1／2／3”用于显示顺序，不承担唯一身份。
- 一次创建只生成一套实验步骤；重复渲染、刷新、保存或请求重试不能重复追加。
- 新实验默认未完成，不能继承规程预览中的已勾选状态。
- 实验应保留创建时使用的规程内容或可追溯版本。之后编辑规程，不得静默改变已有实验的操作内容、进度或备注。
- 对同一来源与版本，规程编辑、规程预览、创建预览、实验预览和执行的操作顺序与内容归属应一致。实验固定旧版而规程已更新时，以版本说明解释差异，不能强行覆盖旧实验来取得表面一致。

## 5. 本次 TRIzol 规程的目标呈现

以下仅用于说明结构，不改写实验条件，不根据截图补写看不见的操作，也不预先指定完整规程最终应有多少步。

**准备资料／用量参考**

- 不同培养规格的工作用量。
- “以下为1个样本的总用量……”等适用范围与分管说明。
- 完整的用量对照表。
- “依据与换算……”及“配比基准……”。

这一部分不生成完成 checkbox，不计入执行进度。表格和操作所需用量应便于查看；较长的参考依据可以收起，但不能连同必需参数一起藏起来。

**步骤1　实验前准备与样本登记**

正文显示标记样本、记录日期与细胞状态等原有操作内容一次，不再单独生成一个“标记样本……”步骤。

**步骤2　去培养液并原位裂解**

正文保留该操作对应的原文和参数，不再把标题与正文分成两个 checkbox。

**步骤3　分管并完成裂解**

正文保留该操作对应的原文、分管说明和相关内容。

其余步骤在读取完整规程后按同一原则整理。不得把这三个示例当成完整的 TRIzol 实验流程。

截图表格中还存在可能难以辨读的相邻数字与“×”组合。请同时检查其在来源、规程和实验中的显示是否被合并或破坏；如原始含义不明确，记录待核对位置，**不要猜测数值、单位或自动修改实验配方**。

## 6. 标题与正文重复的修复

### 6.1 从生成过程纠正

- 有明确操作标题：标题只显示一次，正文包含对应说明，不把相同标题再次复制到正文首行。
- 没有独立标题、只有操作正文：保留正文一次，可使用现有“步骤N”作为简短标签；不要把整段正文复制成加粗标题。
- 仅有标题、没有正文：显示标题一次，不生成重复正文或没有意义的占位段落。
- 一段说明本不应是步骤：将其归入资料区或所属步骤。不能只去掉重复文字后仍把它作为独立步骤保留。

### 6.2 谨慎处理已有重复内容

优先修复生成规则。若需要对既有数据去重，应限定于同一步骤内，并保留前后差异和原始副本。

- 只有能确认是系统生成的完全重复标题块／正文块，才进入自动修复范围。
- 比较时可规范无意义的空白、换行和显示标记，但不得因此合并参数、单位、上下标、公式或不同操作条件。
- 标题与正文相似、但正文补充了剂量、时长、温度、注意事项或附件时，保留补充内容。
- 不按全篇文本去重：不同步骤中相同的洗涤、离心等操作可能是真实重复操作。
- 不用 CSS 隐藏重复项、截断文本或模糊字符串匹配来掩盖数据问题。

目标：每个步骤有一个清晰的标题区、一份正文、一处完成控件。系统生成的额外 checkbox 必须从相应数据或渲染逻辑上消除。

## 7. 执行体验与相关功能

| 功能 | 本次要求 |
|---|---|
| 步骤总数、已完成数、剩余数 | 统一根据实际可执行步骤计算，资料、说明、空块及重复内容不计入。 |
| 勾选与保存 | 只更新当前实验对应步骤；刷新、保存后重开，完成状态不丢失、不串到其他步骤或实验。 |
| 备注／偏差／异常 | 绑定稳定的实验步骤标识，不能在重排后跟错步骤；保留已有记录与时间。 |
| 计时器／计算器 | 原有绑定随实际操作保留；资料块不会因误解析为步骤而额外出现整套执行控件。 |
| 表格／图片／附件 | 内容与所属步骤关系正确，保存回读后仍完整；不能因转换重新上传或重复生成附件。 |
| 实验预览 | 与执行页使用同一份实验步骤数据；可以显示只读步骤状态，但不把每段说明单独勾选化。 |
| 屏幕适配 | 桌面与手机显示相同的操作数量和顺序；长表格可合理横向滚动，手机上的“正文”不得变成额外步骤。 |
| 导出／打印 | 若现有系统支持，保留步骤结构和资料区，不能再次将所有段落扁平化为步骤。 |

精简重复内容的同时，避免用缩小字号、截断正文或隐藏必需说明来压缩页面。不要借本次任务扩大到全站无关 UI 重设计。

## 8. 模板制作与系统兼容性

修复后，为以后新建和导入的规程建立一套简明、可执行的模板约定，并放到仓库现有模板／开发文档中。

1. **分清资料和操作。** 实验目的、适用范围、材料试剂、用量表、方法依据与参考文献使用各自的说明区域；只有真正的操作放入步骤区域。
2. **每一步是一个完整单元。** 操作标题和正文、表格、图片属于同一逻辑步骤；多段正文不能因为换行被拆开。
3. **不要用装饰字符承担数据语义。** `☑`、`□`、加粗或某个标题字号不能作为唯一的步骤识别依据。使用项目已有步骤结构；DOCX 模板则采用可被当前导入器明确识别的样式或结构约定，并由导入后预览核实。
4. **普通编号列表与执行步骤分开。** 材料列表、参考文献编号、步骤内子项不能自动变成主步骤。
5. **保留必要信息。** 单位、上下标、符号、链接和表格在导入、保存、创建、执行与现有导出中保持原意；不得在 UI 整理中改写实验方法。
6. **对接现有功能。** 创建实验、执行进度、工具入口、记录、附件和导出都使用已确认的步骤归属，不能各自从显示文本重新识别。
7. **模板交付前走通全过程。** 新增／修改模板后，必须实际生成规程并创建测试实验，检查预览、执行、进度保存与回读，不能只检查 Word 或规程预览是否好看。

同步修改造成问题的内置模板、示例或模板生成逻辑。对用户自己的旧规程，提供可追溯的结构整理方式；不要要求用户逐份手工重写所有内容来绕开系统问题。

## 9. 其他规程必须怎样检查

### 9.1 先做完整清单

在有权限的测试数据范围内，列出所有现有模板与所有可访问规程的当前版本，逐份给出状态。按实际存在的来源分类，例如手工创建、DOCX 导入、历史富文本或其他受支持来源；不存在的类型不要虚构为已经覆盖。

历史版本若采用不同存储格式，应补充对应格式的代表性回归，不必把相同格式的每个历史版本重复创建实验。已归档、不再用于新建实验的规程可单独列出，并明确是否纳入本次运行检查。

每份当前规程至少检查：

- 预期操作单元及其判定依据；未能确定时标为待整理，不自行编一个正确步骤数。
- 创建后步骤数量、顺序、标题、正文归属与源内容是否一致。
- 非操作说明是否被勾选化；一个操作是否被拆成多个步骤。
- 表格、图片、附件和必要参数是否保留。
- 标题正文重复、双层 checkbox、重复生成或空步骤。
- 实验预览和执行是否一致，进度统计是否正确。

### 9.2 数据核对与视觉检查都要做

自动化遍历可以用于发现结构问题，但必须逐份打开当前规程对应的创建预览、实验预览和执行页面，查看步骤边界及主要内容。长文档需要滚动检查，不能只截首屏。

在隔离测试环境创建临时实验并标识其来源，避免给真实工作区留下大量测试实验。优先用可重置测试数据，不在生产数据上反复勾选、完成或删除实验。

如果没有数据库、登录权限或某类规程的数据，先完成可访问范围内的修复与检查，在交付中列出缺失项及具体原因。不得把“没查到”“没有权限”“只看了模板源码”标成通过。

### 9.3 检查表格式

建议交付 CSV 或 Markdown 表，至少包含：

## 10. 已有实验和历史记录的处理

代码修复不等于既有实验数据自动正确。请单独确认受影响实验是否已保存错误步骤，以及当前处于哪个状态。

| 数据状态 | 处理原则 |
|---|---|
| 后续新建实验 | 直接使用修复后的转换规则和确认过的规程结构。 |
| 尚未开始的草稿实验 | 先输出修复预览；有明确来源映射且不丢内容时，可采用有备份、可回滚的修复流程。保留已有草稿备注或附件。 |
| 已开始／进行中的实验 | 不批量重建或直接删除步骤。先给出旧步骤到新步骤的映射及影响，保留完成状态、备注、附件、操作者和原时间；一对多／多对一关系不明确时不得猜测迁移。 |
| 已完成／已审核等历史实验 | 保留当时的记录与来源版本。本次不要自动重写历史内容和进度；如项目已有更正机制，按该机制提供可追溯的更正方案。 |

说明段落曾经被勾选完成，不代表实际操作已完成。修复时不能据此自动把合并后的真实步骤标为完成，也不能伪造完成时间。

若发现需要历史数据修复，交付范围清单、变更预览、备份与回滚办法；不得仅为让测试通过而删除原实验。迁移执行应与代码修复分开记录，说明哪些已执行、哪些仅准备了方案。

## 12. 实施顺序与最终交付

建议依次执行：复现与保存原始数据 → 找到错误产生环节 → 明确资料和步骤归属 → 修复转换与显示 → 处理问题模板与必要的草稿修复 → 检查所有当前规程 → 实际操作验收。

回归应针对本次已证实的问题和内容／进度完整性风险，不需要为每个样式调整添加重复测试。测试数据不得包含未经脱敏的样本身份信息。

最终向用户交付：

1. **真实根因与代码改动说明**：指出问题在哪一环产生，修改了哪些实际文件，不只列猜测。
2. **本次规程修复前后对照**：资料区、真实步骤、标题正文与进度；总步骤数必须来自完整规程核对。
3. **其他规程检查表**：逐份结果与数量汇总；未能检查的项目和原因单列。
4. **可复用的模板约定与修复后的示例**：确保后续模板能走通创建实验和执行流程。
5. **验证证据**：桌面与窄屏截图；创建、勾选、保存和刷新流程的交互记录或短录屏；实际运行的相关测试结果。
6. **数据修复结果**：区分新建实验已修复、已有草稿已修复、进行中／历史实验的处理状态，附必要的回滚信息。

完成标准：用户从修复后的规程创建实验时，看到的是有正确层级的操作步骤与准备资料；不会因为段落多而冒出一批 checkbox；不会把同一内容重复显示为标题和正文；勾选、记录、工具和来源版本仍保持准确。
