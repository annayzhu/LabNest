## 做得好的地方

1. **体系选择与操作进度分开。** 准备不是“第 1 步”，不会使完成比例虚高。执行页反复展示本次体系，且其他体系位于明示“不适用、不计进度”的 disclosure 中。
2. **量值有上下文。** 参数表把采用值、单位和来源放在同一行，计算回执可看到输入、采用结果、方法版本及近似条件。已完成操作保留禁用的实际值字段，而不是把数据隐藏。
3. **历史保护的语气准确。** 继续实例明确说明原完成记录并未复制为本次完成，显示继续位置并提供返回原记录的链接。按钮“保留原记录，创建继续实例”说明实际行为，避免让用户误以为是在原记录上覆盖。

## 优先问题

### A1 — [P1] 实际值修改后仍可显示旧的“已保存”标签

**证据级别：源码确认的状态风险；本次未修改字段触发。** `StructuredStepRecord.tsx:35` 的输入优先显示本地 `values[field.id]`，其下“已保存 · 时间”仅以服务器是否存在旧值为条件。恢复 sessionStorage 草稿同样可覆盖显示值。没有 dirty 比较，也没有“未保存修改”标记。

**影响：** 一项已有实际记录被改写但尚未保存时，屏幕可同时出现新数值与旧“已保存”回执。研究人员被打断后回来，无法凭就地状态判断眼前数值是否已经入库。这里的问题是状态表达失真，不是本次已证实的数据丢失。

**建议：** 按字段比较当前值与已保存值。不同则显示“未保存修改”，将服务器值另列为“上次保存：50 µL · 时间”；保存成功后清除对应草稿，恢复“已保存”。正在保存时直接在按钮或字段附近显示进度，失败保留输入并保持未保存状态。

**验收：** 已保存 50 → 本地改为 55 → 不保存/刷新恢复草稿时，55 始终明确标为未保存，50 的回执不能看似属于 55；保存成功后再显示新回执。建议 `$impeccable harden` / `$impeccable clarify`。

### A2 — [P2] 已确认的准备区在手机上仍完整展开，当前操作被推到多屏之后

**证据级别：live 390×844 实看。** 原实例打开后第一屏基本都是准备字段，第一次向下滚动仍在参数/计算回执及体系摘要；再滚动才进入步骤正文和完成按钮。准备区本身没有收起入口，继续实例还默认展开历史。相关位置：`RunSystemPreparation.tsx:30-42,52`。

**影响：** 开始前的核对路径合理；执行中每次重新进入仍要穿过已经确认的资料。单手操作、频繁中断的实验人员最受影响。页面未横向溢出，问题是纵向任务优先级。

**建议：** 首次未确认时展开准备；确认且无本地变更后改为紧凑的“已确认体系 / 版本 / 关键量值”摘要，保留明确“查看或调整”入口。发生变更、缺失参数或错误时自动展开。继续实例保留一行醒目的历史链接与继续位置，历史详情可收起。

**验收：** 390px 已确认实例重新打开，当前步骤在首屏或一次自然滚动内可达，同时体系摘要和历史入口仍可见。建议 `$impeccable adapt` / `$impeccable distill`。

### A3 — [P2] 长规程的“作用内容”把步骤、所有段落和表格行放进同一长列表

**证据级别：live 编写页 AX 与源码。** 当前长正文 fixture 在每个规则的“作用内容”内列出 70 段背景以及步骤、图片、表格行；重复出现 `内容 · rich_text`，还出现 `内容 · media` 和 `{{proteinase}}` 等内部表达。`ProtocolSystemsEditor.tsx:41-44,85` 将所有目标拼为一层，并只截取前 60 字。

**影响：** 规则定位容易选错相似段落。目标 ID 虽稳定，使用者却无法从相同或截断的显示标签识别目标；需离开配置区到正文比对。较短规程受影响较小。

**建议：** 按“步骤 / 正文章节 / 表格行”分组，默认先显示操作区内容，支持筛选；选中后展示章节、完整片段和“定位正文”。空段落用“背景 · 空段落”等可理解标签，媒体用图注或文件名，参数引用显示用户名称。不要把位置当身份替换 stable ID。

**验收：** 在当前 70 段 fixture 中能够准确找到指定表格行或同名段落，且不用记住列表顺序。建议 `$impeccable clarify` / `$impeccable optimize`。

### A4 — [P2] 继续实例的历史实际值丢失字段名称

**证据级别：live 继续页及 `RunSystemPreparation.tsx:52`。** 历史显示“原实际记录：50 µL · 2026-10-14T01:53:40.893Z”，没有“实际 Proteinase K”字段名称；渲染遍历 `[id, v]` 但只展示值、单位和时间。

**影响：** 当前 fixture 只有一个实际字段，仍可通过返回原实例核对；同一步存在两个体积记录时，仅值与单位不能说明测量对象。历史虽被保护，读者仍需要自己重建含义。

**建议：** 历史快照随量值保留并显示原字段名称，例如“实际 Proteinase K：50 µL”，统一本地时间显示并可查原始时间。名称应来自冻结快照，避免后来改名改变历史含义。

**验收：** 一步包含两个同单位实际字段时，继续实例可仅凭历史区明确区分它们。建议 `$impeccable clarify`。

**A1 暂不关闭：仍有两处需要补齐的草稿保留问题。**

1. `StructuredStepRecord.tsx:64` 的“跳过原因”input 未在 pending 时禁用。保存实际值后，用户仍可输入新原因；成功 effect 使用提交瞬间的 `saved.reason` 写回 storage 和 state（30–36 行），会覆盖等待期间的新文字。可通过禁用该输入或按当前值合并未提交字段修复。
2. `ProtocolRunProgressForm.tsx:223,336` 给该组件的 key 包含全局 plan revision。保存实际值、跳过、计时等推进 revision 后，组件会被卸载重建；新实例 `submitted.current` 为空，只恢复新 revision 的 storage 键。成功清理 effect 因此不能可靠保留同一步未提交的原因，也不能迁移其他步骤的实际值草稿。正常服务端 55 回读通过，不能证明旧 storage 已清理或无关草稿保留。需要稳定组件身份及明确跨 revision 的草稿复核/迁移机制，不能把无声消失当成清理成功。

建议追加两个针对性验证：一是“同一步已有未提交跳过原因→保存实际值→原因仍在”；二是“步骤 A 输入未保存实际值→步骤 B 保存或启动计时→返回 A 及刷新后草稿仍明确存在，且新 revision 下不能静默自动提交”。在慢响应期间输入原因的检查用于覆盖第一处并发窗口。父任务负责修复及生产构建后的浏览器验证。
